    公开 API 边界¶

    边界声明¶

    本门户只记录已经批准给模块开发者使用的扩展面。任何未列入该范围的内容，都必须视为内部实现。

    已批准的扩展面¶

    模块基类契约¶

    可公开内容包括：

    • 模块元数据字段；
    • 参数模式约定；
    • 生命周期方法；
    • 指标与元数据访问器；
    • 共享上下文的使用方式。

    注册中心相关概念¶

    可公开内容包括：

    • 注册；
    • 别名支持；
    • 发现与解析概念；
    • 安全实例化预期。

    面向作者的发现规则¶

    • 模块名称必须稳定、可读，并且适合在配置中被引用。
    • 别名只用于兼容性，不应用来替代正式名称。引入别名时，规范名称仍需保留在文档中。
    • 只有当模块通过宿主应用批准的注册或发现路径暴露出来时，才算“可发现”。
    • 动态发现是否开启可能因部署环境不同而变化，模块作者不能假设所有环境都支持自动发现。

    标识与输出规则¶

    • module_id 在同一个策略定义中应保持稳定。
    • 需要供下游消费的输出必须写入可预测的键。
    • indicator_ref 这类下游引用应始终指向文档化的模块标识，而不是依赖隐式顺序。
    • 如果模块输出结构发生变化，这属于契约变更，必须做版本和文档同步。

    校验相关概念¶

    可公开内容包括：

    • 标准排序；
    • 实盘与回测的组合要求；
    • 会影响示例和文档的准备层概念。

    受控扩展区域¶

    执行类扩展不是默认公开定制路径。相较于指标、信号、过滤、风险、sizer、仓位、输出和组合模块，它受到更强的评审、校验和运行约束。

    内部专属内容¶

    以下主题刻意不在本网站展开：

    • 专有执行流程内部细节；
    • 基础设施容器具体实现；
    • 实盘适配协议；
    • 状态持久化机制；
    • 系统级风险执行逻辑；
    • 运维阈值和生产调优信息。

    如何申请边界调整¶

    如果某个模块团队需要把当前内部能力升级为公开契约，应提交文档治理申请，至少包含：

    1. 使用场景；
    2. 建议公开的契约形式；
    3. 安全性与稳定性影响；
    4. 向后兼容预期。

    任何团队都不应在未经批准的情况下，把内部代码片段直接作为外部指导文档发布。
