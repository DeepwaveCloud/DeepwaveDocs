# 公开架构

## 架构意图

模块框架的核心目标，是让策略能力通过多个可复用积木拼装出来，而不是集中写在一个巨大的策略类里。模块作者只需要面向扩展层开发，平台继续掌控编排、校验和运行期服务。

## 面向开发者的安全架构视图

```mermaid
flowchart LR
    A[策略定义] --> B[模块注册中心]
    B --> C[校验与准备]
    C --> D[执行顺序解析]
    D --> E[运行时上下文]
    E --> F[组合模块链]
    F --> G[模块输出]
```

## 可以公开说明的组件

### 模块契约

模块基类定义了生命周期、元数据、参数校验、执行入口和指标接口，是所有模块开发的基础。

### 模块注册中心

注册中心是受控的发现与实例化边界。它负责模块解析、别名支持和动态加载能力，使得扩展模块可以接入平台，而无需修改平台核心代码。

### 校验与准备层

校验负责确认模块集合对目标运行模式是结构正确的。准备层可以在进入运行时之前做顺序标准化以及批准范围内的默认补全。

### 运行时上下文

模块通过共享上下文访问市场数据、上游输出和当前执行态。模块作者应把它当作受控接口，而不是内部系统总线。

## 作者可依赖的上下文 allowlist

普通模块开发只应稳定依赖以下上下文表面：

- 文档化的数据映射中发布的市场派生数据；
- 上游指标结果；
- 上游信号结果；
- 通过稳定模块标识写入的模块输出；
- 宿主运行时显式暴露的当前 bar 或当前时间标记。

除非另有明确契约，不应假设自己可以直接拥有 broker 句柄、传输对象、内部校验标志或宿主管理的运行时状态。

## 模块作者的设计约束

- 模块逻辑应聚焦业务职责。
- 不要假设可以直接访问内部基础设施服务。
- 不要把环境细节硬编码到模块中。
- 不要依赖未文档化的顺序副作用。
- 不要把上下文当成随意写入的全局存储。

## 依赖注入建议

平台整体使用依赖注入管理基础设施，但模块作者不应依赖容器内部结构。若测试需要替身，应在宿主应用或测试装配层完成 provider override，而不是在模块内直接绑死容器实现。

## 安全边界

适合对外公开的内容包括：

- 模块类型与职责；
- 排序规则；
- 生命周期方法；
- 元数据与参数模式职责；
- 不涉及内部细节的组合示例。

不适合对外公开的内容包括：

- 事件总线内部实现；
- 执行适配器拓扑；
- 实盘状态同步内部链路；
- 后端集成秘密信息。
